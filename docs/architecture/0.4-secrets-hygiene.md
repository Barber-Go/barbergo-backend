Formato mínimo del `.env.example` (reescritura completa). Cada sección incluye propósito, si es required/opcional, cómo generar si es secret.

```

# Core (required siempre)
# ─────────────────────────────────────────────────────────────────────────────
# DATABASE_URL — PostgreSQL connection string (Railway provee el valor en prod)

# PORT — puerto HTTP del backend (Railway lo inyecta en prod; local por defecto 3000)

# ─────────────────────────────────────────────────────────────────────────────
# Auth (required)
# ─────────────────────────────────────────────────────────────────────────────
# JWT_SECRET — secreto para firmar tokens JWT. MIN 32 chars. NUNCA el valor default.
#   Generar con: openssl rand -hex 64
JWT_SECRET="<generar con: openssl rand -hex 64>"

# JWT_EXPIRES_IN — duración del JWT (ej. 7d, 24h, 3600s)
JWT_EXPIRES_IN="7d"

# ─────────────────────────────────────────────────────────────────────────────
# Encryption (required — credenciales SII)
# ─────────────────────────────────────────────────────────────────────────────
# ENCRYPTION_KEY — AES-256 key en hex. EXACTO 64 hex chars = 32 bytes.
#   Consumida en src/shared/crypto.utils.ts para cifrar claves tributarias SII.
#   Generar con: openssl rand -hex 32
ENCRYPTION_KEY="<generar con: openssl rand -hex 32>"

# ─────────────────────────────────────────────────────────────────────────────
# Frontend URL (required — redirects de Webpay/MP)
# ─────────────────────────────────────────────────────────────────────────────
# FRONTEND_URL — URL pública del mobile para callbacks de pagos
FRONTEND_URL="https://app.barbergo.cl"

# ─────────────────────────────────────────────────────────────────────────────
# Cloudinary (required)
# ─────────────────────────────────────────────────────────────────────────────
CLOUDINARY_CLOUD_NAME="<cloud name de la cuenta — ej. deqpmiq9u>"
CLOUDINARY_API_KEY="<api key del dashboard Cloudinary>"
CLOUDINARY_API_SECRET="<api secret del dashboard Cloudinary>"

# ─────────────────────────────────────────────────────────────────────────────

# ─────────────────────────────────────────────────────────────────────────────
ANTHROPIC_API_KEY="<sk-ant-... del console.anthropic.com>"

# ─────────────────────────────────────────────────────────────────────────────
# Google AI — Gemini (required si AI Estilos activo)
# ─────────────────────────────────────────────────────────────────────────────
GOOGLE_AI_API_KEY="<AIza... de Google AI Studio>"

# ─────────────────────────────────────────────────────────────────────────────
# Webpay — Transbank (required)
# ─────────────────────────────────────────────────────────────────────────────
# TRANSBANK_ENV — 'integration' (sandbox) o 'production'
TRANSBANK_ENV="integration"
TRANSBANK_COMMERCE_CODE="597055555532"
TRANSBANK_API_KEY="<api key Transbank — el sandbox viene preconfigurado en el SDK>"

# ─────────────────────────────────────────────────────────────────────────────
# Mercado Pago (required)
# ─────────────────────────────────────────────────────────────────────────────
# MP_ENV — 'sandbox' o 'production'. NUEVA en bloque 0.4. El backend valida
#   que el prefijo de MP_ACCESS_TOKEN coincida (TEST- vs APP_USR-).
MP_ENV="sandbox"
MP_ACCESS_TOKEN="<TEST-... en sandbox | APP_USR-... en producción>"

# ─────────────────────────────────────────────────────────────────────────────
# SII — apigateway.cl (required si módulo tributario activo)
# ─────────────────────────────────────────────────────────────────────────────
SII_API_BASE_URL="https://app.apigateway.cl/api/v2"
SII_API_TOKEN="<token de apigateway.cl — actualmente: ver CLAUDE.md o Railway>"
SII_EMISOR_RUT="<RUT emisor sin puntos, ej. 21387505-1>"
```

## 10. Riesgos y mitigaciones

| Riesgo | Probabilidad | Impacto | Mitigación |
|---|---|---|---|
| **Rotación de `ENCRYPTION_KEY` invalida credenciales SII ya persistidas** — si algún `BarberProfile` tiene `claveTributaria` cifrada con la vieja llave, el dueño no podrá emitir boletas hasta re-cifrar. | Media | Alto | Antes de rotar: (1) `ops` hace `SELECT COUNT(*) FROM "BarberProfile" WHERE "siiClaveEncrypted" IS NOT NULL;` (o equivalente en TaxProfile). (2) Si count >0, correr script admin one-shot que lee cada registro con la llave vieja, re-cifra con la nueva, persiste. (3) Setear nueva llave en Railway y redeploy. (4) Validar con el caso de Renato (es el dueño de barbería real en prod). **Asunción:** si count = 0, rotar libremente. |
| **Rotación de `JWT_SECRET` invalida tokens activos → usuarios deslogueados** | Alta | Medio | Comunicar antes. Elegir ventana horaria de baja carga. La re-autenticación es trivial desde el mobile. No es blocker. |
| **Validación de startup muy estricta rompe desarrollo local** (ej. un dev olvida setear `ANTHROPIC_API_KEY` y no puede arrancar) | Alta | Medio | La lista de required vs opcional debe ser cuidadosa. Marcar como **required solo**: `DATABASE_URL`, `JWT_SECRET`, `JWT_EXPIRES_IN`, `ENCRYPTION_KEY`, `MP_ENV`, `TRANSBANK_ENV`. Las demás (ANTHROPIC, GOOGLE_AI, SII_*, CLOUDINARY_*, MP_ACCESS_TOKEN cuando `MP_ENV=sandbox`) quedan como opcionales con warning al startup, no error fatal. Documentar en `.env.example`. |
| **Guard de MP_ENV rechaza configuración actual en Railway** si el token productivo no matchea el prefijo esperado | Baja | Alto | Antes de deployar el guard, `ops` inspecciona `railway variables get MP_ACCESS_TOKEN` y setea `MP_ENV` de forma coherente. Rollout en dos pasos: primero setear `MP_ENV` en Railway, segundo deployar el código que lo valida. |
| **Build EAS del mobile ignora `.env` local** — las env `EXPO_PUBLIC_*` en builds nativos vienen del entorno de build, no de `.env`. Si no hay `eas.json`, la preview va a tener `EXPO_PUBLIC_CLOUDINARY_CLOUD=undefined` y el fallo seguro va a abortar todos los uploads en la build. | Alta | Medio | Documentar explícitamente que antes del primer `eas build --profile preview`, hay que setear las env vars con `eas env:create` o un `eas.json` con `build.preview.env`. En Expo Go local este riesgo no aplica (lee `.env`). Agregar a los criterios de aceptación un smoke test en EAS preview cuando `eas.json` exista (marcar como TODO en el futuro bloque). |
| **Secretos filtrados en logs** — el constructor de `MercadoPagoService` podría loggear el token completo por error | Media | Alto | El loggeo explícito mostrar **solo** `MP_ENV` y `token=${prefix}...${last4}` (prefijo hasta el primer guión + últimos 4 chars). Nunca el token completo. Verificar en code review de `backend-feature`. |
| **Cloud name Cloudinary de dev termina en producción** por confusión | Media | Medio | La confirmación con Sebastián (sección 8) + `.env.example` marcando claramente "coincide con CLOUDINARY_CLOUD_NAME del backend" + variable EAS distinta por profile (`preview`=dev, `production`=prod) cuando se arme `eas.json`. |
| **Desarrolladores nuevos no generan secretos y usan placeholders literales** (ej. `<generar con: openssl rand -hex 64>` como valor real) | Media | Alto | La validación de startup cubre esto: cualquier `JWT_SECRET` con `<` o con `change-me` o <32 chars falla. Agregar explícitamente el patrón `<generar` a la lista de `forbidden`. |
| **`.env` de `barbergo-mobile` ya está en el repo con un valor productivo** (auditoría muestra que tiene `EXPO_PUBLIC_API_URL=https://barbergo-backend-production...`) | Media | Bajo | Verificar si `.env` está tracked. Si lo está, **no** borrar del historial (ese API URL es público), pero moverlo a `.env.example` y dejar `.env` ignorado. El `EXPO_PUBLIC_API_URL` es información pública por diseño (aparece en builds de producción), no es un secreto. |

## Apéndice — Nota agregada durante pre-flight (2026-04-23)

Durante los CHECKs previos a la invocación de agentes se encontró que **hay tres columnas cifradas con `ENCRYPTION_KEY`**, no dos como asumía el plan original:

| Tabla (DB) | Modelo (Prisma) | Columna | Notas |
|---|---|---|---|
| `barbers` | `BarberProfile` | `claveTributaria` | Clave SII del barbero. AES-256-GCM. |
| `tax_profiles` | `TaxProfile` | `siiClaveEncrypted` | Clave SII de la barbería. AES-256-GCM. |
| `tax_profiles` | `TaxProfile` | `pfxPassword` | Password del certificado .pfx de la barbería. AES-256-GCM. |

**Implicancias para PARTE 2 (rotación `ENCRYPTION_KEY`)**:

- El script one-shot de re-cifrado debe leer y re-cifrar **las 3 columnas**, no 2.
- El `COUNT(*)` pre-rotación debe incluir `pfxPassword IS NOT NULL`.

**Hallazgo de naming confirmado en DB**: todas las tablas tienen `@@map` a snake_case (`barbers`, `tax_profiles`), pero las **columnas** siguen en camelCase. Queries SQL directas requieren comillas dobles en columnas (`"claveTributaria"`) pero no en nombres de tabla.

**Hallazgo de modo Mercado Pago**: el token productivo actual empieza con `APP_USR-` → el backend está cobrando **dinero real** ahora mismo. El rollout del guard `MP_ENV` debe ser en dos pasos estrictos:
1. `ops` setea `MP_ENV=production` en Railway antes del deploy.
2. `backend-feature` + `ops` segunda pasada deployan el código que lee y valida `MP_ENV`.

Si se invierte el orden, el startup post-deploy aborta (`MP_ENV` ausente) y baja producción.

**Hallazgo de variables SII en Railway**: existen 5 (no 3 como en el plan): `SII_API_BASE_URL`, `SII_API_TOKEN`, `SII_CLAVE`, `SII_EMISOR_RUT`, `SII_RUT`. El `.env.example` del backend debe documentar las 5.
