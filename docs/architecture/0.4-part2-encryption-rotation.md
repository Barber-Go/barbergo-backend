# Bloque 0.4 — PARTE 2: Rotación de ENCRYPTION_KEY con re-cifrado
_Planificado: 2026-04-23_

> Documento hermano de `0.4-secrets-hygiene.md` (PARTE 1 ya completa: JWT_SECRET rotado + código B-2 deployado + 4/4 validaciones pass). Esta PARTE 2 cierra la superficie pendiente: rotar `ENCRYPTION_KEY` en prod y re-cifrar las 3 filas cifradas con AES-256-GCM, sin corromper ninguna.

---

## 1. Objetivo

Rotar `ENCRYPTION_KEY` en Railway de su valor actual a uno nuevo (64 hex chars, 32 bytes) ejecutando un script one-shot local que re-cifra, en una sola transacción Postgres atómica, las credenciales SII persistidas (`barbers.claveTributaria`, `tax_profiles.siiClaveEncrypted`, `tax_profiles.pfxPassword`), con verificación post-write dentro de la misma transacción y rollback automático si cualquier fila falla la verificación. Cierra el último ítem pendiente de higiene de secretos de la Ola 0 antes de abrir bloques de features.

## 2. Alcance

### Incluido
- **Script one-shot**: `scripts/rotate-encryption-key.ts` — TypeScript, corre localmente con `railway run npx ts-node scripts/rotate-encryption-key.ts`. No se deploya a Railway (no entra en el build del backend).
- **Helpers duplicados in-script**: `encryptWith(key, plaintext)`, `decryptWith(key, packed)`, `tryDecryptWith(key, packed)` — implementan el mismo AES-256-GCM que `src/shared/crypto.utils.ts`, pero con la key pasada como **parámetro explícito** en vez de leerla de `process.env.ENCRYPTION_KEY`. Justificación: evita que un bug de env setting (ej. variable no exportada, shell rc file sobrescribiendo) termine usando la key equivocada sin darse cuenta, y permite que el mismo proceso sostenga OLD y NEW simultáneamente.
- **Testing combinado**:
  - **T2 — unit tests** con fixtures sintéticas (plaintexts hardcodeados cifrados con una OLD key conocida, el test corre la función de rotación contra esos fixtures y verifica round-trip).
  - **T1 — integration tests** contra una DB local clonada desde prod vía `pg_dump | psql` (clon one-shot a `barbergo_rotation_test` localhost). Valida conteos, contenido, idempotencia, rollback en dry-run, rollback en falla simulada.
- **Runbook de ejecución en madrugada** (3–5 AM): orden de comandos, checkpoints de confirmación manual, puntos de no-retorno, criterios de abort.
- **Script inverso para rollback** post-commit: el mismo script re-ejecutado con las keys invertidas, más procedimiento alternativo de restore por `pg_dump`.
- **CHANGELOG**: entrada fechada en `CHANGELOG.md` (o crear el archivo si no existe) con hash de commit del script, hashes de los dos valores de key (solo los primeros 8 chars para trazabilidad, NO la key completa), conteo de filas afectadas, y timestamp de rollout.
- **Limpieza**: instrucciones para destruir la OLD key de forma segura después del smoke test post-rollout.

### Explícitamente excluido
- **No se toca `src/shared/crypto.utils.ts`**: sigue leyendo `process.env.ENCRYPTION_KEY` como hoy. Su contrato no cambia. El script duplica el algoritmo para no acoplarse a esa lectura de env.
- **No se cambia `.env.example`**: PARTE 1 ya lo versionó con la plantilla de `ENCRYPTION_KEY`. Este bloque no lo vuelve a tocar.
- **No se agregan endpoints**: el script es CLI puro, no hay ruta HTTP nueva.
- **No se modifica el schema Prisma**: las 3 columnas ya existen con el tipo correcto (`String?`).
- **No se modifica lógica de negocio** que invoca `encrypt`/`decrypt` (`barbers.service.ts`, `tax-compliance.service.ts`, `sii.service.ts` quedan intactos).
- **No se implementa KMS/Vault** ni rotación automática recurrente (futuros bloques).
- **No se deploya el script a Railway** (vive solo en repo + ejecución local).
- **No se cambia el algoritmo** (sigue AES-256-GCM con formato `iv:authTag:ciphertext` hex).

## 7. Orden de ejecución entre agentes

### Paso 1 — `architect` (YO, este documento). Completado.

### Paso 2 — `backend-feature`
Implementa y testea **antes** de cualquier acción en producción:
1. Crear `scripts/rotate-encryption-key.ts` siguiendo el pseudocódigo de la sección 10/Apéndice.
2. Crear `scripts/__tests__/rotate-encryption-key.unit.test.ts` (T2):
   - Fixture: generar una OLD key fija (64 hex hardcodeado en el test), cifrar 5 plaintexts conocidos con ella, armar un objeto mock de "filas".
   - Probar: round-trip (decrypt con NEW da el mismo plaintext), idempotencia (correr 2 veces no cambia nada la segunda), falla de verificación fuerza rollback, keys iguales → exit 20, key de formato inválido → exit 20, MODE inválido → exit 20.
3. Crear `scripts/__tests__/rotate-encryption-key.integration.test.ts` (T1):
   - Setup: clonar DB prod a local una sola vez (comando documentado para Renato, fuera del test).
   - Probar contra DB local: conteos pre/post, commit real en MODE=apply, rollback real en MODE=dry-run, rollback real si inyectamos fila corrupta.
4. Correr `npm run test` local → ambos pasan.
5. Correr `npx tsc --noEmit` → sin errores.
6. Abrir PR en GitHub con el diff. **No mergear todavía**. Renato revisa + aprueba antes del rollout.

### Paso 3 — `ops` (primera pasada, preparación)
Antes de la noche del rollout:
1. Verificar que el PR del `backend-feature` está aprobado.
2. Generar la nueva key: `openssl rand -hex 32` → guardar en un `.txt` local (gitignored) junto con un backup doble: una copia en un password manager de Renato. Cero copias en Railway todavía.
3. Leer la OLD key: `railway variables get ENCRYPTION_KEY` → guardarla en el mismo `.txt` local como `OLD=...`. Verificar que son distintas y ambas son 64 hex.
4. Correr el script en modo `dry-run` contra la DB local clonada → debe salir con exit 0 y log "DRY RUN: 3 rows would be rotated, 0 skipped, 0 failed".
5. Dry-run contra prod: `railway run` inyecta `DATABASE_URL` de prod, pero **MODE=dry-run** fuerza rollback al final → valida que el script efectivamente puede leer las 3 filas de prod con la OLD key. Exit 0 esperado. Esto se corre 1 vez de día (lunes-miércoles 10-18h), NO en la ventana de madrugada, para no confundir logs.
6. **Pre-backup explícito**: `pg_dump` de la DB productiva a `~/backups/barbergo-prod-YYYYMMDD-HHMM-pre-rotation.sql.gz`. Verificar tamaño > 0 y que `gunzip -t` pasa.
7. Mergear el PR del script a `main`.

### Paso 4 — `ops` (segunda pasada, rollout en madrugada)
Ventana 3:00–5:00 AM. Ver runbook detallado en Apéndice A.

Secuencia resumida:
1. Pre-checkpoint: backup fresco otra vez (el del paso 3 puede tener minutos), sesión Railway activa, las dos keys en shell env vars locales.
2. "Pausar" Railway: dos opciones evaluadas (ver riesgo #4):
   - **Opción A (preferida)**: `railway variables set ENCRYPTION_KEY=invalid-stub-to-force-abort` (cualquier valor ≠ 64 hex) → el próximo startup aborta en `validateEnv`. Esperar 30s a que el deploy actual termine. Si hay replicas corriendo, `railway redeploy` fuerza el restart y la nueva réplica no arranca. Servicio en 503.
   - **Opción B (fallback)**: eliminar temporalmente `ENCRYPTION_KEY` de Railway variables y redeployar.
3. Correr `MODE=apply ENCRYPTION_KEY_OLD=<old> ENCRYPTION_KEY_NEW=<new> railway run npx ts-node scripts/rotate-encryption-key.ts` desde laptop local. Esperar exit 0. Leer post-counts y elapsed.
4. Setear nueva key en Railway: `railway variables set ENCRYPTION_KEY=<new>`.
5. `railway up` → deploy con la nueva key. Esperar health check ok.
6. Smoke test (ver sección 9).
7. Si smoke test OK → destruir la OLD key (ver sección 8, paso 5).
8. Si smoke test FAIL → ejecutar rollback (Apéndice B).

### Paso 5 — `ops` (tercera pasada, post-rollout)
1. Appendear CHANGELOG.
2. Confirmar destrucción de OLD key.
3. Documentar cualquier desviación del runbook como Lessons Learned en el CHANGELOG.

**Razón del orden**: `backend-feature` va antes de cualquier acción en prod porque el script se testea exhaustivamente antes de tocar datos reales. `ops` se divide en 3 pasadas porque hay checkpoints largos (preparación con dry-run, ejecución nocturna, limpieza post). `db-schema` **no participa** (no hay schema).

7. **Smoke test endpoint** — identificado por el agente `backend-feature` durante FASE B-5.2 (2026-04-23):

   **Endpoint elegido: `GET /api/v1/barbers/me/sii-credentials`**

   - **Archivo origen**: `src/barbers/barbers.controller.ts:119` → `src/barbers/barbers.service.ts:230` (`getSiiCredentials`).
   - **Guards**: `JwtAuthGuard + RolesGuard` con `Roles(BARBER, BARBER_INDEPENDENT, BARBER_EMPLOYEE)`.
   - **Por qué este**: es el único de los cuatro consumidores de `decrypt(claveTributaria)` en el runtime que (a) ejecuta el decrypt en el camino feliz y (b) **no tiene efectos colaterales externos**. Los otros tres viven en `src/sii/sii.service.ts` y todos pegan al SII real: `emitirBoletaParaBooking` (línea 139) emite una BHE contra `apigateway.cl` — irreversible; `getBoletaPdf` (línea 279) descarga un PDF real y requiere una boleta previamente emitida; `anularBoleta` (línea 338) invalida un documento tributario. Ninguno es aceptable como smoke test. `getSiiCredentials`, en cambio, sólo lee la fila de `barbers`, llama `decrypt(profile.claveTributaria)` y devuelve el plaintext en el payload de la respuesta — prueba directa y no destructiva de que el ciphertext post-rotación es válido bajo la NEW key.

   **Comando (2 pasos: login → smoke)**

   ```bash
   # Paso 1 — obtener JWT de un usuario barbero con credenciales SII ya configuradas.
   # El usuario `barbero@test.com / 12345678` del seed de CLAUDE.md satisface la precondición,
   # siempre que su BarberProfile tenga rutTributario + claveTributaria en la base
   # (i.e. sea una de las 2 filas de barbers con claveTributaria != NULL que el script procesó).
   JWT=$(curl -sS -X POST \
     -H "Content-Type: application/json" \
     -d '{"email":"barbero@test.com","password":"12345678"}' \
     https://barbergo-backend-production.up.railway.app/api/v1/auth/login \
     | jq -r '.access_token // .data.access_token')
   echo "$JWT" | cut -c1-20    # sanity: debe empezar con "eyJ"

   # Paso 2 — smoke test: decrypt bajo la NEW key
   curl -sS -i \
     -H "Authorization: Bearer $JWT" \
     https://barbergo-backend-production.up.railway.app/api/v1/barbers/me/sii-credentials
   ```

   **Respuesta esperada (HTTP 200)**

   ```json
   {
     "rut": "21387505-1",
     "tipoClave": "tributaria",
     "clave": "<clave SII del barbero, en texto plano tras decrypt>"
   }
   ```

   **Criterio de éxito**

   - Status `200 OK`.
   - El campo `clave` viene como string no vacío. Cualquier fallo de auth-tag GCM (ej. si el UPDATE post-rotación guardó basura o si la NEW key de Railway no es la que usó el script) se manifestaría como `500 Internal Server Error` con un stack trace de `ERR_OSSL_EVP_BAD_DECRYPT` / `Unsupported state` en los logs de Railway.
   - El campo `rut` debe matchear el RUT tributario conocido del usuario de prueba (`21387505-1` según CLAUDE.md) — doble check de que estamos pegándole al usuario correcto, no a un barbero equivocado.

   **Precondición de datos**

   - Existe un `BarberProfile` asociado al `User` con email `barbero@test.com`, con `rutTributario` NOT NULL y `claveTributaria` NOT NULL. Los conteos pre-flight (2 barbers con `claveTributaria`) garantizan que al menos un barbero de prueba califica; si el seed no lo dejó listo, el usuario debe setearlo vía `PATCH /api/v1/barbers/me/credenciales-sii` con cualquier clave de prueba **antes** del rollout (no durante la ventana).

   **Fallback si falla el login del usuario de prueba**: reemplazar el paso 1 por un JWT de cualquier otro `BARBER*` con credenciales SII configuradas. La lista se puede obtener con `SELECT u.email FROM users u JOIN barbers b ON b.\"userId\" = u.id WHERE b.\"claveTributaria\" IS NOT NULL` desde la DB pre-rotación.

   **Mitigación de riesgo residual**: este endpoint devuelve la clave SII en plaintext en la respuesta HTTP. Ejecutarlo únicamente desde la terminal de Renato durante la ventana de rollout (nada de proxies, nada de herramientas que persistan historial HTTP). Al terminar el smoke test, limpiar el buffer de la terminal y no pipear la respuesta a archivos.

## 10. Riesgos y mitigaciones

| # | Riesgo | Probabilidad | Impacto | Mitigación |
|---|---|---|---|---|
| 1 | **Proceso del script abortado a mitad** (Ctrl+C accidental, WiFi cae, laptop se suspende, terminal cerrada). | Media | Alto | `prisma.$transaction` con isolation level `Serializable` asegura rollback automático cuando la conexión se corta. Postgres revierte la tx entera al detectar desconexión. No hay escrituras parciales. Mitigación adicional: correr desde laptop con cable ethernet si posible, `caffeinate -d` en macOS para evitar suspensión, `screen` o `tmux` para que el cierre de terminal no mate el proceso. Exit code del script en este caso es 30 (ABORTED_BY_USER) si captura SIGINT; de lo contrario muere con SIGKILL y la tx rollbackea por desconexión. |
| 2 | **Clonado de DB local incompleto** (pg_dump corta antes, red inestable, disco lleno) → integration test pasa pero no valida todas las filas reales. | Media | Medio | Antes de correr T1, verificar conteos: `psql barbergo_rotation_test -c "SELECT COUNT(*) FROM barbers WHERE \"claveTributaria\" IS NOT NULL;"` debe dar **2**. Si da 0 o 1, rechazar el clon y re-hacer `pg_dump`. Documentar este check como pre-condición del test en el runbook. |
| 3 | **Olvido de destruir OLD key** post-smoke-test → secreto viejo sigue vivo en `.txt` local y password manager indefinidamente. | Alta | Medio | Timer explícito en el runbook: tras smoke test verde, agendar recordatorio de "destruir OLD key" a 7 días (168h) (por ejemplo `at` en macOS o un evento de calendario). La ventana de 7 días (168h) es intencional (colchón para rollback tardío). Después de 7 días (168h) sin issues, destruir con `shred`/`rm -P` y remover del password manager. |
| 4 | **Railway tarda >60s en pausar** o `railway up` de re-activación dispara un deploy implícito que interfiere con el script en curso. | Media | Alto | Usar Opción A (set `ENCRYPTION_KEY=stub`) que es instantánea — el guard `validateEnv` de PARTE 1 aborta el startup en ms. Confirmar con `curl /api/v1/health` que responde 503 antes de empezar el script. No hacer `railway up` hasta que el script termine con exit 0 y el `railway variables set ENCRYPTION_KEY=<new>` haya confirmado. El script en sí no llama a `railway up` ni `railway` nada — es pura lectura/escritura SQL. |

## Apéndice B — Script inverso (rollback post-commit)

### Opción (a) — re-ejecutar el mismo script con keys invertidas (**preferida**)

Requisito: OLD key preservada (`.txt` local + password manager).

```
railway variables set ENCRYPTION_KEY="stub-forces-abort-$(date +%s)"    # pausa otra vez

railway run npx ts-node scripts/rotate-encryption-key.ts
# Esperar exit 0
railway variables set ENCRYPTION_KEY="$ENCRYPTION_KEY_NEW"               # que es la original
railway up
```

Ventaja: reutiliza código testeado, tiempo <5min.
Desventaja: si el fallo del smoke test fue porque el script tiene un bug de encoding/formato, correrlo al revés puede replicar el bug.

### Opción (b) — restore pg_dump (**fallback si (a) falla**)

```
railway variables set ENCRYPTION_KEY="stub-forces-abort-$(date +%s)"
# Descargar .sql.gz del backup
gunzip -c ~/backups/barbergo-prod-*-pre-rotation.sql.gz | railway run psql $DATABASE_URL
# (alternativa: pg_restore si se hizo pg_dump -Fc)
railway variables set ENCRYPTION_KEY="<OLD key original>"
railway up
```

Ventaja: restaura el estado exacto pre-rotación, cubre cualquier bug del script.
Desventaja: pierde cualquier escritura en tablas **no tocadas por el script** que haya ocurrido entre el backup y el rollout (la ventana 3–5 AM minimiza esto a ~0 writes, pero documentar).

### Opción (c) — combinación

Intentar (a) primero. Si exit no-0 o smoke test sigue fallando después de (a), ir a (b). Documentar cuál se usó en CHANGELOG.

## Apéndice C — Pseudocódigo detallado del script

```
main():
  // Validación de env
  assert ENCRYPTION_KEY_OLD is 64 hex chars                  // else exit 20
  assert ENCRYPTION_KEY_NEW is 64 hex chars                  // else exit 20
  assert ENCRYPTION_KEY_OLD !== ENCRYPTION_KEY_NEW           // else exit 20
  assert MODE in {'dry-run', 'apply'}                        // else exit 20, default 'dry-run'

  oldKey = Buffer.from(ENCRYPTION_KEY_OLD, 'hex')
  newKey = Buffer.from(ENCRYPTION_KEY_NEW, 'hex')

  // Pre-check de DB
  db = await prisma.$queryRaw<{current_database: string}>`SELECT current_database()`
  log("Connected to DB: ${db.current_database}")
  // Sanity: si el DB name parece local, confirmar interactivamente o abortar
  if (db.current_database.includes('local') || db.current_database.includes('test')) {
    if (!process.env.FORCE_LOCAL) exit 20
  }

  // Handlers de señal
  process.on('SIGINT', () => { log('ABORTED BY USER'); exit 30 })

  // Counts pre-rotación
  preCounts = {
    barbers_claveTributaria: SELECT COUNT(*) FROM barbers WHERE "claveTributaria" IS NOT NULL,
    tax_profiles_siiClaveEncrypted: SELECT COUNT(*) FROM tax_profiles WHERE "siiClaveEncrypted" IS NOT NULL,
    tax_profiles_pfxPassword: SELECT COUNT(*) FROM tax_profiles WHERE "pfxPassword" IS NOT NULL,
  }
  log("Pre-counts:", preCounts)

  start = Date.now()
  rotated = 0
  skipped = 0

  try {
    await prisma.$transaction(async (tx) => {
      // ——— Tabla barbers.claveTributaria ———
      rows = await tx.barber.findMany({ where: { claveTributaria: { not: null } }, select: { id: true, claveTributaria: true } })
      for (const row of rows) {
        // Idempotencia: si ya está con NEW, skip
        if (tryDecryptWith(newKey, row.claveTributaria!)) {
          log("barbers.id=${row.id.slice(0,8)}: already NEW, skip"); skipped++; continue
        }
        // Decrypt con OLD
        plaintext = decryptWith(oldKey, row.claveTributaria!)   // throw si falla
        // Re-encrypt con NEW
        newCipher = encryptWith(newKey, plaintext)
        // Update
        await tx.barber.update({ where: { id: row.id }, data: { claveTributaria: newCipher } })
        // Verify dentro de la tx (re-read desde tx, no cache)
        reread = await tx.barber.findUnique({ where: { id: row.id }, select: { claveTributaria: true } })
        verified = decryptWith(newKey, reread.claveTributaria!)
        if (verified !== plaintext) throw new Error(`verification failed for barbers.id=${row.id}`)
        log("barbers.id=${row.id.slice(0,8)}: re-encrypted OK"); rotated++
      }

      // ——— Tabla tax_profiles.siiClaveEncrypted ———
      rows = await tx.taxProfile.findMany({ where: { siiClaveEncrypted: { not: null } }, select: { id: true, siiClaveEncrypted: true } })
      for (const row of rows) {
        if (tryDecryptWith(newKey, row.siiClaveEncrypted!)) { skipped++; continue }
        plaintext = decryptWith(oldKey, row.siiClaveEncrypted!)
        newCipher = encryptWith(newKey, plaintext)
        await tx.taxProfile.update({ where: { id: row.id }, data: { siiClaveEncrypted: newCipher } })
        reread = await tx.taxProfile.findUnique({ where: { id: row.id }, select: { siiClaveEncrypted: true } })
        if (decryptWith(newKey, reread.siiClaveEncrypted!) !== plaintext) throw new Error(...)
        log("tax_profiles.siiClaveEncrypted id=${row.id.slice(0,8)}: OK"); rotated++
      }

      // ——— Tabla tax_profiles.pfxPassword ———
      rows = await tx.taxProfile.findMany({ where: { pfxPassword: { not: null } }, select: { id: true, pfxPassword: true } })
      for (const row of rows) {
        if (tryDecryptWith(newKey, row.pfxPassword!)) { skipped++; continue }
        plaintext = decryptWith(oldKey, row.pfxPassword!)
        newCipher = encryptWith(newKey, plaintext)
        await tx.taxProfile.update({ where: { id: row.id }, data: { pfxPassword: newCipher } })
        reread = await tx.taxProfile.findUnique({ where: { id: row.id }, select: { pfxPassword: true } })
        if (decryptWith(newKey, reread.pfxPassword!) !== plaintext) throw new Error(...)
        log("tax_profiles.pfxPassword id=${row.id.slice(0,8)}: OK"); rotated++
      }

      // Forzar rollback en dry-run
      if (MODE === 'dry-run') {
        throw new Error('DRY_RUN_ROLLBACK')   // código de control, no error real
      }
    }, {
      isolationLevel: 'Serializable',
      timeout: 45_000,
      maxWait: 10_000,
    })

    // Commit exitoso (solo en apply)
    elapsed = Date.now() - start
    log("ROTATION COMPLETED: ${rotated} rotated, ${skipped} skipped, elapsed=${elapsed}ms")
    // Post-counts (confirma idempotencia)
    postCounts = ...
    log("Post-counts:", postCounts)
    assert deepEqual(preCounts, postCounts)   // conteo de NOT NULL no cambia
    exit 0

  } catch (err) {
    if (err.message === 'DRY_RUN_ROLLBACK') {
      elapsed = Date.now() - start
      log("DRY RUN: ${rotated} would be rotated, ${skipped} skipped, rollback forced, elapsed=${elapsed}ms")
      exit 0
    }
    log("ROLLED BACK:", err.message)
    exit 10
  } finally {
    await prisma.$disconnect()
  }


// ——— Helpers locales al script ———
// Deliberadamente duplicados de src/shared/crypto.utils.ts para NO leer process.env.ENCRYPTION_KEY.
// Justificación: un bug de env setting (shell rc sobrescribiendo, variable no exportada) podría hacer
// que crypto.utils.ts opere con la key equivocada. Al pasar la key como parámetro explícito tipado,
// el único path de input es el argumento — imposible confundir OLD con NEW.

encryptWith(key: Buffer, plaintext: string): string {
  iv = randomBytes(16)
  cipher = createCipheriv('aes-256-gcm', key, iv)
  encrypted = cipher.update(plaintext, 'utf8') ++ cipher.final()
  authTag = cipher.getAuthTag()
  return `${iv.hex}:${authTag.hex}:${encrypted.hex}`
}

decryptWith(key: Buffer, packed: string): string {
  [ivHex, authTagHex, ciphertextHex] = packed.split(':')
  decipher = createDecipheriv('aes-256-gcm', key, Buffer.from(ivHex, 'hex'))
  decipher.setAuthTag(Buffer.from(authTagHex, 'hex'))
  return decipher.update(Buffer.from(ciphertextHex, 'hex')) ++ decipher.final()
}

tryDecryptWith(key: Buffer, packed: string): string | null {
  try { return decryptWith(key, packed) }
  catch { return null }
}
```
